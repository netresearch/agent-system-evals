Open Forward Reviews

Does the Netresearch agent engineering stack change how an agent handles a realistic request — one that does not say what to do?

Review this TYPO3 extension and tell me what needs attention.

The setup

A real TYPO3 extension, frozen at one historical commit. The agent receives the single sentence above and nothing else: no framework version, no tool to run, no file to open, no category of finding to produce. Working that out is what is being measured.

Two configurations, three runs each. Everything is held constant except the skills: same repository, same commit, same model (Claude Code on claude-opus-5), same grader, same environment, same trial count.

controlClaude Code on its own
mainClaude Code plus eight Netresearch skills, pinned to released versions

Grading does not ask "did it find the expected bugs" — an open question has no fixed answer key. It asks how the work was done, across eight aspects: did it establish what the project is; did it reach a systematic route; did each claim come from the source that owns that fact; are findings anchored to a place and a consequence; were the available checks actually run; is the most important thing first; did it assert anything it never established; and could a developer act on the result.

Two dimensions move

Routing is the larger number and the weaker evidence: control has no injected skills, so part of that gap is definitional. Not all of it — the grader counted Claude Code's own entry points as available and scored their non-use as a routing failure. Prioritization moves from 0.61 to 0.94, and nothing about that is definitional.

Nothing else moves

Five dimensions sit within noise at this sample size, and outcome quality is 1.00 on both sides. On this case both configurations produce a review a developer could act on. What changes is the shape of the work, and what it costs.

Source authority fails on both sides

0 of 3 either way. The mechanical evidence is identical in all six runs: no external canonical source was consulted, and the resolved dependency state was never read. Every statement about framework version support, in every run, rests on recollection rather than on a lookup — and a version constraint states what is permitted, not what is installed or tested.

What this does not show. One case, one agent, one model, three runs per side. This is one measurement, not a verdict on the stack. The small negative differences are within noise, and reading them as harm would be exactly the overreach that reporting counts instead of averages exists to prevent.

What the agents actually found

Both configurations produced substantive reviews. The leading finding in the unaided run was a cache-clearing middleware registered in the frontend stack that never checks whether a user is authenticated — anchored to file and line, with the consequence stated: any anonymous visitor can flush page caches. Neither that nor two further findings appear in the case's recorded background notes; the agent established them from the code.

The reviewed commit also carries three security findings marked with inline suppression comments. A static analysis run reports clean there while the problems remain, which is what lets the case distinguish an agent that reads a green result as reassurance from one that asks what produced it.

Method

2 × 3runs, one fleet apart
8graded dimensions per run
15/15harness acceptance criteria met

Execution, isolation, skill injection, trajectory recording and regrading are provided by Harbor. This project contributes the review methodology, the cases, the eight-dimension rubric and the conventions that keep results comparable. Grading rests on observable behaviour only — tool calls, commands, files opened, output seen, the resulting diff and the final answer. Stated intentions are not evidence, and private reasoning is never read.

The agent cannot reach the reviewed repository's own forge during a run: the working copy is a single-commit fetch with the remote removed, and the network allowlist excludes it while still permitting the framework's canonical documentation. The later change that fixed several of the issues lives in that repository's future and stays out of reach.
